# 架构评审：渲染机的职责边界

> 对象：`video-auto-cut` ｜ 日期：2026-09-22
> 依据：`docs/dependency-graph.html`（22 节点 / 40 边）+ 源码逐处实证（引用均给出文件与行号）

## 摘要

**当前的 `worker.mjs` 不是"渲染机"，而是"第二台全功能业务机"。**

依赖图上两者可达集重合 19/20，唯一差集是 `express · multer` —— 也就是说，除了"用 HTTP 收上传、托管前端页"，渲染机需要的东西和业务机一模一样，包括最重的 483MB whisper 模型和智谱 API 密钥。

核心成因不是"忘了优化"，而是一个被压平的正交决策：**任务分派依据的是"阶段（`kind`）"，而不是"能力（`capability`）"**；再叠加 `proxy.mp4` 的落盘位置被物理绑定在 `base` 的执行位置，一个中间文件就把"AI 环境需求"和"渲染环境需求"钉死在了同一台机器上。

好消息是：**修法所需的基础设施已经存在且在运行**（`steps` / `rerender` 早就在跨机搬运 `base` 的产物），因此不需要造新组件，只需改分派策略 + 一个一行的上下文补丁。

---

## 一、背景：这个问题是怎么被发现的

### 1.1 依赖图给出的读数（客观事实）

| 读数 | 数值 | 出处 |
|---|---|---|
| `server` 直接出边 | `→ pipeline, jobs, config, public(asset), extWeb(ext)` | 图 168-170 / 197 / 206 |
| `worker` 直接出边 | `→ pipeline, jobs, config` | 图 171-173 |
| 共有出边 | 3 条，**逐条相等**（非"接近"） | 同上 |
| 差集 | 2 条，**全部落在 Web 层** | 同上 |
| 可达集 | 业务机 20 / 渲染机 19，**重合 19/20** | 传递闭包统计 |
| 唯一差集节点 | `extWeb`（express · multer） | — |

精确表述：`worker = server − Web 层`。

而这个减法**减错了地方**：被减掉的 express / multer 与静态托管，是整个项目里最轻的部分（只负责收发与托页）；项目真正的"重"——ffmpeg、whisper、LLM、Chrome——**一条都没被减掉**。

### 1.2 图能证明"重合"，但证明不了"为什么"

19/20 的重合度容易让人误以为"这是设计好的分工"。实际不是。要定位原因，必须从图上走出来，看两个**模块图天然画不出**的事实：

- 图**画不出**"节点运行时需要什么环境"——`py-trans` 在图上只是一个节点名，"被依赖"≠"环境已就绪"；
- 图**画不出**"产物落盘在哪台机器"。

这两条恰恰是问题的真正所在。

## 二、核心成因

### 2.1 直接成因：分派依据是"阶段"，不是"能力"

`src/server.js:98-120`：

```
function dispatchOrRun(job, kind, steps) {
  if (workerOnline()) {                      // 渲染机在线 → 一律派发
    dispatchQueue.push({ jobId: job.id, kind, steps });
  } else if (…) {                            // 刚掉线 10 分钟内 → 仍排队等它
    dispatchQueue.push({ jobId: job.id, kind, steps });
  } else {
    const task = kind === "base"             // 离线 → 本地兜底
      ? () => runBase(job, …)
      : …;
    enqueueLocal(job, task);
  }
}
```

`kind` 只有三个取值：`"base"` / `"steps"` / `"rerender"`。它**原本描述的是"流水线的哪一段"，却被直接当成了"该派给谁"的依据**。于是只要渲染机在线，`base` 就被一起派了出去——见 `src/server.js:216` 的 `dispatchOrRun(job, "base")`。

一个决策变量同时承担了两个正交语义（**阶段** 与 **宿主**），这是问题的起点。

### 2.2 中层成因：`base` 是一个"三合一"的异构包

`src/lib/pipeline.js:430 runBase()` 内部**严格串行**做三件彼此无关的事：

| 子阶段 | 实现 | 资源画像 | 依赖 |
|---|---|---|---|
| 转码 | `makeProxy` | I/O 密集 | ffmpeg |
| 转写 | `transcribe` → `asr.js` → `transcribe.py` | CPU 密集 + 大文件 | Python、faster-whisper、`models/` 483MB |
| LLM 决策 | `decideCut` → `llm.js` | 网络密集 | `ZHIPU_API_KEY`、公网出口 |

链路是：转码出 `proxy.mp4` → 抽 `audio.wav` → 转写 → 用转写结果调 LLM（`pipeline.js:441 / 450 / 460 / 499`）。**每一步都是下一步的前置，任何一步都不能跳过。**

后果：**"这台机器要不要 AI 环境"被压成了一个二值问题——要么全有，要么 `base` 跑不动。** 没有"只转码不转写"这种中间形态。

### 2.3 根本成因：`proxy.mp4` 把两种环境钉在了一起

这是整个问题的锁扣。

- `src/lib/pipeline.js:3`（文件头注释）：产物链 `proxy.mp4 → step-cut.mp4 → step-captions.mp4 → step-mg.mp4`（每步输入 = 上一步输出）；
- `src/lib/pipeline.js:527 runCut()`：读**本机** `workDir/proxy.mp4` 作为裁剪底片；
- `src/lib/pipeline.js:421-422 latestOutput()`：本机找不到任一 `step-*.mp4` 时回退 `proxy.mp4`，否则抛错；
- `src/lib/pipeline.js:890-893 rerenderStep()`：两者皆无则抛 `"输入视频不在本机"`。

**`proxy.mp4` 是整条步骤链唯一的外部输入，它由 `base` 产生，并且落在 `base` 执行的那台机器上。** 于是形成一条硬绑定：

```
base 跑在哪台机器  →  proxy.mp4 就落在哪台机器
                   →  那台机器必须有能力产出它
                   →  必须有 ffmpeg + whisper + 模型 + LLM key
```

而"渲染机优先"的派发策略，恰好让 `base` 默认落在渲染机。所以渲染机**必须**背全套 AI 环境——这不是部署时的疏忽，是架构里写死的。

那句断言本身就是自白：

```
if (!fs.existsSync(proxy)) throw new Error("proxy.mp4 缺失（base 未完成？）");
```

它表面是"链入口检查"，实质是**环境绑定的声明**：这个文件在哪，整套 AI 环境就得在哪。

### 2.4 反向证据：搬运机制早就存在，只是没用在自己身上

`src/server.js:161-165` 的派发上下文清单：

```
base      → ["input.mp4", "job.json"]                              // 只有原始素材
steps     → ["transcript.json","plan.json","cut-axis.json", …]     // 已含 base 产物
rerender  → ["captions.json","step-cut.mp4","proxy.mp4", …]        // 连底片都搬
```

`steps` 与 `rerender` **早就在把 `base` 的产物跨机搬运了**——`transcript.json`、`plan.json`，甚至 `proxy.mp4` 本身都在清单里。

结论很重要：**"把产物送到另一台机器"这套机制是现成的、正在运行的，唯一没有用上它的，就是 `base` 自己。** 这直接决定了修法是"改分派策略"而不是"造新设施"。

## 三、对系统的影响

| # | 影响 | 机制 | 严重度 |
|---|---|---|---|
| 1 | **部署成本线性复制** | 每加一台渲染机 = 复制一套业务机环境（含 483MB 模型与完整 Python 环境） | 高（成本） |
| 2 | **密钥扩散面 = 渲染机数量 + 1** | 每台 `worker` 的 `.env` 都必须持有 `ZHIPU_API_KEY` | 高（安全） |
| 3 | **横向扩展边际收益递减** | 加渲染机的初衷是并行提速（Remotion 是 CPU 密集、可并行），但每台的部署与维护成本不降，扩展收益被环境成本吃掉 | 中 |
| 4 | **失败面按机器数放大** | `base` 的失败模式（模型缺失、key 失效、拉模型超时）被复制到每台机；任一机环境漂移，该机接到的任务全挂 | 高 |
| 5 | **失败点靠后** | 转码通过、抽 wav 通过、卡在转写——**分钟级之后**才报错，前面几步全都"看起来正常" | 中 |
| 6 | **首次运行的外网依赖被重复承担** | `models/` 不存在时 `whisperModel` 回退 `"small"`，走 hf-mirror 现下 483MB；每台新渲染机都要在首次任务里再经历一次，耗时不可控 | 中 |
| 7 | **故障定位分片** | 同一任务可能跑在业务机（兜底路径）或渲染机（派发路径），同一条报错出现在不同机器的日志里 | 中 |
| 8 | **结果一致性风险** | `base` 在两处执行同一份代码，版本漂移时产物不同；而版本不一致**只 warn 不阻断**（`src/worker.mjs:263`）→ 用户可能看到"同一视频两次结果不同" | 中高 |

**一个必须点明的因果汇聚**：影响 2（密钥扩散）、影响 6（模型重复下载）、以及此前"两份部署指南里明文写 key"这件事，**是同一个成因的三个表现**——

> 因为 `base` 需要在多台机器上执行，所以模型和密钥必须在多台机器上存在；
> 因为"把 key 分发到 N 台机器"很麻烦，所以部署时有人图省事把 key 写进了文档。

治理其中任何一个表现而不动成因，都只是把问题挪个地方。

## 四、改进建议

按"改动面 × 收益"排序。P0 / P3 属 L1–L2 增量（低风险，可直接做）；**P1 调整部署形态、P2 改动分派范式，均触碰 L0，需先确认再动**。

### P0 · 接单前 preflight（fail-fast）— 立即可做

**优化方向**
在 `runBase` 入口与 `worker` 领单处做能力自检：ffmpeg / ffprobe 可执行、`transcribe.py` 存在且可被 Python 调起、`models/` 就绪或可下载、`ZHIPU_API_KEY` 存在且可探活。**失败立即报明确错误，不进入转码。**

**预期收益**
把"跑 5 分钟后失败"提前到"接单即失败"；错误信息直接指向缺失组件。消掉影响 5（失败点靠后）与影响 7（误归因）。零架构风险，可独立验证。

**落地注意事项**
- **不要把 `cv2` 列为硬性前置**：`src/python/facedetect.py` 对 cv2 缺失是**优雅降级**（`found:false, exit 0`），硬校验会误杀可用环境。
- key 的"可用性"校验只做存在性 + 一次极小探活（如 1 token 的 `glm-5.3-flash` 调用），不要做重量级自检。
- `models/` 缺失是**合法状态**（回退联网下载），只能是 warn 不能是 error，但要显式提示"首次任务将下载约 483MB"。

### P1 · 把 `base` 收回业务机（执行位置调整）— ★核心修法

**优化方向**
`dispatchOrRun` 中 `kind === "base"` 不再派发，直接走 `enqueueLocal`。`src/server.js:113-114` **已经写好这条分支**，只是被 `workerOnline()` 的优先级盖住了——本质是把优先级反过来。渲染机从此只接收 `steps` / `rerender`。

**预期收益**

| | 现状 | P1 之后 |
|---|---|---|
| 渲染机环境 | Node + ffmpeg + Chrome + Python + faster-whisper + **models/ 483MB** + **ZHIPU key** + cv2 + public | Node + ffmpeg + Chrome + Python + cv2 + public |
| 最重的两项 | 必须常驻 | **彻底不再上机** |

影响 2（密钥扩散）、影响 4（失败面放大）、影响 6（模型重复下载）**同时消解**；新增渲染机的边际成本从"复制一台业务机"降为"装一套渲染栈"。

**落地注意事项（3 个必改点 + 2 个权衡）**

1. **必须把 `proxy.mp4` 加入 `steps` 的 `contextFiles`（`src/server.js:165`）。**
   这是本方案**唯一的硬性补丁**。原因见 §2.3：渲染机的 `runCut` 读本机 `proxy.mp4`，而目前的 `steps` 清单里只有 json 文件、没有底片。不加这一行，渲染机第一步 `cut` 就会抛 `"proxy.mp4 缺失（base 未完成？）"`。
2. **派发时序必须在 `base` 完成之后。**
   现有流程由前端在分析完成后触发 `steps`，天然满足；但改动后要**显式复核**这一点。理由：`src/worker.mjs:136-137` 的注释已记录过同类坑——「本地旧版可能是 paused 态，复用会把业务机状态覆盖回去」。
3. **`src/worker.mjs:162` 的 `base` 分支不要删**，改为开关（如 `ALLOW_BASE=1`），留给"业务机性能弱、需要把 base 一并外包"的部署形态。
4. **权衡 A（带宽 vs 算力）**：`proxy.mp4` 是百 MB 级文件，改为跨机传输后每任务多一次上/下行。但传输是**一次性**的（`worker.mjs:140` 本地已有即跳过），而背 483MB 模型是**永久性**的——权衡明显有利。
5. **权衡 B（业务机成为瓶颈）**：`base` 收回后，单任务转写 3–6 分钟会串在业务机上。若业务机核数允许，用 `enqueueLocal` 的并发度控制；否则保留 1 台"带 base 能力"的渲染机做混合调度（此时 P2 是必要配套）。

### P2 · 能力声明式分派（capability-based dispatch）— 触碰 L0，需先冻结

**优化方向**
`worker` 心跳时上报能力集（如 `caps: ["render","mg","bgm"]`），业务机按任务**实际需要的能力**选机，而非"在线就派"。

**预期收益**
把"渲染机该有什么"从**默认假设**变成**显式契约**；影响 1、4 从根上消除，同时让 P1 的开关形态自然落地。

**落地注意事项**
- 涉及心跳协议变更（`src/server.js:145-146`、`src/worker.mjs:255-263`），**新旧版本必须能共存**；建议带协议版本号，不匹配时降级为"全能力假定"而**不是**拒绝服务。
- 属 L0（分派范式），按架构流程须先冻结确认，不在本建议的立即执行范围。

### P3 · 一致性：版本阻断 + 溯源

**优化方向**
把 `src/worker.mjs:263` 的 warn 升级为——版本不一致时**拒绝领取需要执行 `base` 的任务**（其余任务放行）；同时在 `job.json` 记录 `executedBy`（主机标识）与 `workerVersion`。

**预期收益**
消掉影响 8；出问题时能回答"这个成品是哪台机器、哪个版本跑出来的"。

**落地注意事项**
不要做**严格相等**比对（不同机器可能只差 patch 号），建议只比对"流水线版本"这一个语义化字段，避免人为阻断正常任务。

### P4 · 密钥治理

**优化方向**
`ZHIPU_API_KEY` 只保留在业务机；若确需渲染机跑 base，让渲染机经业务机**代理**调用 LLM（渲染机不直持 key），或下发短时 token。

**预期收益**
把"密钥扩散面 = 渲染机数量 + 1"压回 **1**，从根上消掉"为部署方便把 key 写进文档"的动机。

**落地注意事项**
若同时执行 P1，本条收益大部分被 P1 覆盖。**P1 优先，P4 作为 P1 不被采纳时的兜底。**

### 明确不采用

- **不引入消息队列、不改技术栈**：单机小工具规模，现有内存 `dispatchQueue` 足够，引入 MQ 只增加运维面。
- **不为 `base` 单独起一个常驻服务进程**：属于过度设计，收益远小于其运维成本。
- **不重命名 `worker.mjs` / `lib/pipeline.js`**：`src/` 迁移刚完成，避免短期内二次大范围扰动。

## 六、落地顺序与验收标准

| 阶段 | 改动位置 | 验收标准 |
|---|---|---|
| P0 | 新增 1 个 preflight 函数，`runBase` 入口 + `worker` 领单处调用 | 故意移除 Python / 置空 key，**启动即报明确错误**，且不进入转码 |
| P1 | `src/server.js` 2 处（`dispatchOrRun` 优先级 + `steps` 的 `contextFiles` 加 `proxy.mp4`）；`src/worker.mjs` 1 处（base 分支加开关） | 业务机跑 base、渲染机跑 steps，完整跑通一个「一键全自动」任务；**渲染机 `.env` 中不含 ZHIPU key 仍能出片** |
| P3 | `src/worker.mjs:263` 的 warn → 条件阻断；`job.json` 增字段 | 人为改版本号后，需要 base 的任务被拒、其余任务正常 |

**改动面总结：P0+P1 合计只动 3 个文件、4 处，不触碰 `src/lib/pipeline.js` 的编排逻辑。** 这是本次建议可控性最高的地方——问题出在"谁执行"，而修法也只需改"谁执行"。

## 七、待确认事项

1. **是否采纳 P1（`base` 收回业务机）**——这会改变分布式部署的职责划分，属 L0 边界调整，需确认后再动。
2. **业务机是否具备承载 `base` 的算力**——多任务并发时，转写会串行排队；若业务机为 2 核，需重新评估（`src/server.js:106` 的注释已提到"大文件在 2 核机龟速跑"这一顾虑）。
3. **P2 能力声明分派是否纳入下一轮**——需先冻结心跳协议版本。
4. **P4 是否保留**——取决于 P1 是否落地。

## 附：一句话版本（给未来的自己）

> 渲染机之所以"重"，不是因为它在渲染时有多重，而是因为它**顺手把 `base` 也干了**；而 `base` 之所以跟着它走，是因为分派代码用 `kind` 一个变量同时回答了"到哪个阶段"和"在哪台机器"两个问题——再加上 `proxy.mp4` 只认本机路径。**把这两件事解开，渲染机自己就轻了。**
